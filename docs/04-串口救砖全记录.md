# 04 — 串口救砖全记录（KPW3 软砖 → 修复）

**症状**：执行极简定制后重启，卡在开机动画（大树+进度条），电源键无响应，插 USB 电脑无反应。

**根因**：当时版本的 minimalize 把 `demd` 禁用了，而 `lab126.conf` 的启动条件是 `start on started system_setup_after_shpm and started demd`。demd 不存在 → lab126（powerd/wifid/volumd/USB 等全部核心守护）永不启动 → 系统死在半初始化状态。

本记录展示完整的串口救砖路径，同样适用于任何"系统起不来但硬件没坏"的 KPW3 软砖。

## 1. 硬件连接

KPW3 主板上留有串口调试触点（无需拆屏，只需撬开前框露出主板）：

- 位置：主板中部偏右、屏蔽罩附近，丝印 **SERIAL DEBUG**，两个并排小触点：**左 RX、右 TX**；
- GND：USB 充电口的金属外壳即可；
- 电平：**1.8V**（关键！3.3V/5V 都不行）；
- 参数：**115200 8N1**；
- USB-TTL 模块必须带电平切换（本项目用 FT232RL 模块，跳线帽拨到 1V8 档）；
- 接法：模块 TX → 主板 RX，模块 RX → 主板 TX，模块 GND → USB 口外壳；**模块的 VCC/5V/3.3V 引脚一律不接**（Kindle 由自己的电池供电）；
- 触点很小，建议焊接；杜邦线虚接是大概率事件（见踩坑记录）。

参考拆机与点位图：https://blog.tama.guru/record/264.html

## 2. macOS 侧工具链（与 Windows 的差异点）

- FT232RL 免驱（macOS 内置 AppleUSBFTDI），设备出现为 `/dev/cu.usbserial-XXXX`；
- **坑 1：stty 设置的波特率不会保持**。USB 设备每次重新枚举（拔插、瞬断），termios 重置为默认 9600。用 `cat` 监听时必须由持有 fd 的同一进程设置波特率。本项目用 python3 标准库（无需装 pyserial）：

```python
import os, termios
fd = os.open("/dev/cu.usbserial-XXXX", os.O_RDWR | os.O_NOCTTY | os.O_NONBLOCK)
a = termios.tcgetattr(fd)
a[0] = 0; a[1] = 0; a[2] = termios.CS8 | termios.CREAD | termios.CLOCAL; a[3] = 0
a[4] = termios.B115200; a[5] = termios.B115200
termios.tcsetattr(fd, termios.TCSANOW, a)
# 然后循环 os.read(fd, 4096)
```

- **坑 2：多个进程读同一串口会互相抢字节**，各拿一半数据，看起来就是"乱码"。任何时候保证只有一个读取者（`lsof /dev/cu.usbserial-*` 检查）。
- **坑 3：回环测试先行**。把模块自己的 TX-RX 短接，发字符串应原样收回——这一步能在碰 Kindle 之前排除模块/驱动/跳线问题（本项目实测：跳线帽虚插导致模块看似正常实则 IO 没电，回环立刻暴露）。
- **坑 4：USB 物理接触**。救砖过程中模块瞬断会导致监听进程拿到失效 fd，静默丢数据。固定好线材，监听进程异常退出后必须重启（不是重开文件）。

## 3. 获取 u-boot 命令行

1. 监听就绪后，给 Kindle 断电重启。**注意**：砖状态下电源键归已死的 powerd 管，长按无效——直接**拔电池排线 10 秒**再插回，保证冷启动（墨水屏冻住的大树画面可能只是几小时前那次启动的残影，不能作为判断依据）。
2. u-boot 输出 `Hit any key to stop autoboot: 1 0`——窗口只有 1 秒，用脚本以 10Hz 持续发 `\n` 即可稳定打断，拿到 `uboot >` 提示符。
3. 打断后停止发送，避免按键灌进后续命令行。

## 4. 这台 u-boot 的特点（lab126 2009.08 定制版）

- `printenv` **输出为空**——环境变量不持久化，全是编译内嵌默认；
- 命令极少：`boot / bootm / bist / idme / md / mw / setenv / run ...`，**没有 mmc/nand/fatload/ext2load**，无法手动从存储加载内核；
- 但 `setenv bootargs ...` 后 `boot`，内嵌 bootcmd 会**沿用你设的 bootargs**——这就是突破口。

## 5. 串口登录为什么走不通（"bad salt"）

正常启动的日志里其实有 `Welcome to Kindle! / kindle login:`，getty 是活的。但：

- 经典 root 密码算法 `fiona + md5(序列号+"\n")[7:11]`（kindlepass）算出的密码登录返回 **`login: bad salt`**——本固件的 `/etc/shadow` 里所有账号的哈希位都是无效值（盐缺失），**任何密码都不可能登录**，包括 framework/mario。
- 结论：不要浪费时间试密码，直接走 u-boot + init 路径。

## 6. 修复：init=/bin/sh 拿 root shell

在 `uboot >` 下：

```
setenv bootargs console=ttymxc0,115200 root=/dev/mmcblk0p1 rw init=/bin/sh
boot
```

- KPW3 根分区是 `/dev/mmcblk0p1`（ext3）；
- 内核起来后直接进 root shell（`sh: can't access tty; job control turned off / #`），文件系统按 `rw` 挂载；
- 修复动作（本项目案例）：

```sh
mv /etc/upstart/demd.conf.disabled /etc/upstart/demd.conf
sync
reboot -f
```

- 修完系统正常启动，日志里能看到 `info demd:starting...::`，随后 lab126/X/桌面链全部起来。

## 7. 验证

- 串口日志从 `perfd: starting...` 之后继续滚动（修复前就停在这里）；
- 屏幕进入 KOReader/原生界面；电源键恢复响应。

完整启动日志（脱敏）见 `assets/bootlog-excerpt.txt`，复刻时可逐段比对确认自己处于哪个阶段。

## 附：本次诊断用到的关键证据点

| 现象 | 结论 |
|---|---|
| 串口一个字节都没有 | 线/模块/电平问题，不是系统问题（u-boot 无条件打印） |
| 收到数据但全是 00 | 电平档位高于 1.8V，信号越不过识别阈值 |
| 收到密集乱码 | 波特率错（USB 重枚举后 termios 掉回 9600） |
| 日志停在 `perfd: starting...` | upstart 卡死点，对照 conf 依赖找被禁的服务 |
