## 1. 总览：架构、分区与体量

### 1.1 系统架构

- **内核**：3.0.35-lab126（`rootfs/lib/modules/3.0.35-lab126/`），ARM EABI5 用户态
- **init**：upstart。`/sbin/init` 是一个 shell 包装脚本（`rootfs/sbin/init`），根据内核 cmdline 选择 upstart 或 sysv，最终 `exec /sbin/init.exe`。默认 `/etc/init -> /etc/upstart`（符号链接）；sysv 备用配置在 `/etc/sysv/`（含 `rcS.conf`、`rc-sysinit.conf` 等），`/etc/inittab` 与空的 `/etc/init.d/` 仅为 sysv 模式/兼容残留
- **GUI 栈**：X11（Xorg + awesome WM + blanket 合成/屏保层，由 `lxinit` 拉起）→ Java cvm（"framework"，Amazon 定制 Java SE8 VM）→ KPP 原生应用（KPPMainApp 首页/商店、KFX reader 等）。5.16 是 Java framework 与原生 KPP 并存的混合架构
- **IPC**：LIPC（`lipcd`，`rootfs/etc/lipc-daemon-*.conf`）+ D-Bus，是全系统的神经中枢，大量 job 和电源事件都走 lipc
- **shell/工具**：busybox 为主 + Amazon 自研守护进程（powerd、cmd、wifid、volumd 等）

### 1.2 分区布局（依据 `rootfs/etc/default/layout`、`rootfs/etc/fstab`）

| 分区 | 挂载点 | 文件系统 | 说明 |
|---|---|---|---|
| mmcblk0p1 | / | ext3，默认只读 | 本 rootfs |
| mmcblk0p2 | （diags） | — | 诊断/工程模式分区（DIAG_P=p2） |
| mmcblk0p3 | /var/local | ext3，读写 | 持久配置、日志、崩溃计数（LOCAL_P=p3） |
| mmcblk0p4 | /mnt/base-us → fuse → /mnt/us | vfat | 用户存储（USB 导出的"Kindle 盘"） |

另有一个按需挂载的 `/keys` 分区（`rootfs/etc/upstart/filesystems_keys.conf`），KPW3 上 `BOARD_DHA_VERSION=none`（`rootfs/etc/sysconfig/platform_variables`），实际不启用。

### 1.3 squashfs loop 挂载（关键！）

`rootfs/etc/loopbacktab` + `rootfs/etc/upstart/system_cramfs_loopbacks.conf` 把以下目录以 squashfs 只读 loop 挂载（从 /dev/loop/2 起）：

```
/usr/share/X11/xkb  /usr/java/lib/fonts  /etc/kdb.src  /usr/lib/locale
/usr/share/keyboard  /opt/var/local  /etc/uks
```

对应实体文件：`usr/java/lib/fonts.sqsh`（84MB）、`usr/share/keyboard.sqsh`（14MB）、`etc/kdb.src.sqsh`、`etc/uks.sqsh`（4KB）等。**rootfs 里这些目录是空挂载点；要替换内容必须重做 .sqsh 或改 loopbacktab 去掉挂载后用普通目录替代。**

### 1.4 体量分布（du）

- `usr/` 263MB（其中 fonts.sqsh 84MB、icu 17MB、blanket 15MB、keyboard.sqsh 14MB）
- `usr/java/` 99MB（cvm JVM + framework jar 运行时）
- `opt/amazon/ebook/` 48MB（framework Java 代码：lib 37MB jar、booklet 9.3MB）
- `app/` 44MB（KPP 原生应用：KPPMainApp 12MB、KPPOOBEMainApp 7.3MB、lib 13MB）

### 1.5 内存管理

- `rootfs/etc/upstart/zram_setup.conf`：开机建 200MB zram swap
- `rootfs/etc/upstart/system.conf`：/var 为 64MB tmpfs；内存 ≥475MB 时挂 250MB tmpfs 到 /mnt/kfxcache（KPW3 命中）
- framework Java 堆固定 `-Xmx49m -Xms49m`（`rootfs/etc/upstart/framework`），512MB 机器上 Java + KPP + webkit 是主要内存压力源

## 3. 签名验证机制与刷机边界

### 3.1 OTA 包验签

核心文件：`rootfs/etc/upstart/bundlefuncs`（被 `ota-update.conf` source）。

- 支持的包格式：FB02/FB03（整包）、FC02/FD03/FC04/FD04/FL01（差分）、SP01（签名封装）
- **FB03 等"裸包"只有 MD5 + 字节混淆（`munger`，固定置换表），没有密码学签名**——但注意真正的应用流程由 `/usr/sbin/otaup`（shell 脚本）→ OTA 引擎（libotaup.so，见 `/usr/bin/otaupd` 的 ELF 依赖）执行，引擎内部还有校验，不能只凭 bundlefuncs 判断全部边界
- **SP01 封装层有真签名**：`verify_bundle()` 用
  `openssl dgst -sha256 -verify $(get_key_path $OTA_CERT) -signature ...` 验签
- 密钥选择（`get_key_path`，bundlefuncs:373-387）：
  - `CERT_1K → /etc/uks/pubprodkey01.pem`
  - `CERT_2K → /etc/uks/pubprodkey02.pem`
  - `CERT_DEV → /etc/uks/pubdevkey01.pem`，**仅当存在 `/PRE_GM_DEBUGGING_FEATURES_ENABLED__REMOVE_AT_GMC` 时才返回**，否则拒绝
- `/etc/uks` 由 `etc/uks.sqsh`（4KB）loop 挂载而来（见 1.3）。导出目录里 `/etc/uks/` 为空属正常（挂载点）

### 3.2 越狱后的刷机边界

- LanguageBreak 装入开发者密钥（往 uks 里加 dev key / 或替换 uks.sqsh）+ 放置 PRE_GM 标志后，`CERT_DEV` 路径打通，自制 SP01 包即可通过 `openssl dgst -sha256 -verify` 验签 → 可刷自制更新包
- rootfs 内的边界就到此为止：rootfs **不负责**内核/u-boot 验签。`extracted/imx60_wario/uImage.sig`、`u-boot.bin.sig` 由 u-boot/安全启动链校验，属于 SoC 层面，改 rootfs 不影响它，反过来自制包里的内核/u-boot 部分仍受底层签名约束
- 更新执行时序（`ota-update.conf`）：检查电量阈值（默认 ≥15%，`/mnt/us/system/SKIP_BATTERY_CHECK_FOR_UPDATE` 可跳过）→ `parse_bundle` → 需要时 `stop framework` → `initctl emit ota-update`（lab126、x 等都 `stop on ... ota-update`）→ `exec /usr/sbin/otaup "${BUNDLE}"`

## 6. OTA 升级机制与屏蔽方案

### 6.1 机制

- 后台检查/下载：`otaupd`（`etc/upstart/otaupd.conf`）、`otav3`（`otav3.conf`），均 `start on started lab126`，nice 2 常驻
- 执行：`ota-update.conf` job（`initctl emit ota-update` / 手动 `updatewait` 等触发）→ `/usr/sbin/otaup`
- 手动包：把 `update_*.bin` 放 /mnt/us 根目录，系统菜单"更新您的 Kindle"走同一 ota-update 通道
- `etc/crontab/root` 里 otacheck 那行在 upstart 模式下是注释状态（`/sbin/init` 的 do_upstart/do_sysv 会切换注释），且本固件无 `otacheck` 二进制——5.16 的 OTA 检查已完全收进 otaupd/otav3
- 更新时会 `stop framework`、`stop on ... ota-update` 停 GUI，并要求电量 ≥15%（`BATTERY_MIN_CHARGE`）

### 6.2 屏蔽方案（对应社区 renameotabin）

社区标准做法 "rename OTA binaries" 在本固件对应的具体文件：

1. **改名/移除二进制**（需 `mntroot rw` 或在自制包里删）：
   - `/usr/bin/otaupd`
   - `/usr/bin/otav3`
   - 视激进程度：`/usr/sbin/otaup`、`/usr/sbin/updatewait`、`/usr/sbin/updatetime`
2. **掐 job**：清空或删除 `etc/upstart/otaupd.conf`、`etc/upstart/otav3.conf` 的 `start on` 行
3. **保留** `etc/upstart/ota-update.conf` + `/usr/sbin/otaup`：这是越狱后刷自制包/官方手动包的入口，删了以后想刷机只能走 diags
4. 辅助：iptables（`etc/sysconfig/iptables`）追加 OUTPUT 规则屏蔽亚马逊更新域名；或干脆常开飞行模式
5. 注意 rootfs 默认只读，改名前必须 `mntroot rw`（`etc/upstart/functions` 提供），改完 `mntroot ro`

## 7. 开机直达 KOReader 的推荐实现

目标：保住硬件抽象层（powerd 电源管理、触屏、EPDC、WiFi、lipc），砍掉 Java framework + KPP 全家桶，启动即进 KOReader。

### 推荐方案（改动最小、可回退）

1. **掐掉 Java framework**：在 /mnt/us 放标志文件 `DONT_START_FRAMEWORK`
   —— 这是 `framework.conf:11` 官方内置开关，framework 不启动则 `framework_ready` 不发出，下游 webreader/scanner/stored/dmld/clickstream/fastmetrics/whisperstore 等全部自然不起。**一行都不用改。**
2. **掐掉 KPP 原生应用**：`kppmainapp.conf` 同时 `start on started lab126_gui`（不经 framework_ready），需显式处理——把 `etc/upstart/kppmainapp.conf`、`kfxreader.conf`、`kfxview.conf` 的 start on 注释掉，或把 `/app/bin/KPPMainApp` 改名（pre-start 有 `[ -x /app/bin/KPPMainApp ]` 检查，改名即静默跳过，最干净）
3. **新增 `/etc/upstart/koreader.conf`**：

```
start on started lab126_gui
stop on stopping lab126_gui or ota-update
respawn
script
  source /etc/upstart/env
  exec /mnt/us/koreader/koreader.sh 2>>/tmp/koreader.err
end script
```

   hook 在 `started lab126_gui` 的理由：此刻 X/blanket、触屏、powerd、wifid、/mnt/us 全部就绪，而 Java/KPP 已被第 1、2 步拦下，内存最干净。KOReader 官方 Kindle 启动脚本本身会通过 lipc 与 powerd 对接休眠/唤醒，架构完全兼容。
4. **可选**：在 koreader.conf 之前先 `stop lab126_gui` 的替代写法（`start on x_setup_ready`）也行，但 x_setup_ready 时 /mnt/us 刚挂载、进度条还在，观感不如 lab126_gui 之后。

### 备选方案

- 直接改 `kppmainapp.conf` 的 `exec /app/bin/KPPMainApp` 为自有 launcher（先弹 KUAL 式菜单再进 KOReader/微信读书），白捡现成的 respawn 和崩溃恢复（KPPMainAppCrashRecovery）逻辑
- 微信读书：走 Android 不现实（i.MX6 单核 512MB 跑不动）；可行路径是 KOReader 插件/网页版（pillow 被禁则无浏览器，需自评），或用 KOReader + 微信读书网页版需要保留 pillow——这是方案取舍点

## 8. 风险清单

1. **lab126_gui 崩溃计数陷阱**（`lab126_gui.conf`）：GUI 侧连续重启 ≥3 次会 reboot，持久重启计数 ≥2 次会触发"客服页面"shutdown 模式（写 /var/local/halt_reason=2）。自定义 KOReader job 若崩溃循环，可能牵连此逻辑。调试期建议先手动 `initctl` 验证再上电自启
2. **rootfs 只读**：所有 /etc、/app 改动都要 `mntroot rw`，或做成自制 SP01 更新包刷入；断电时序不当可能损坏 ext3（虽然 noatime + e2fsck 保护）
3. **/mnt/us 是 vfat + fuse**：KOReader 放 /mnt/us 有 noexec（`fstab` 中 /mnt/us noexec！）——KOReader 启动脚本需要 bind-mount 或复制到 /var/local/tmp 执行，社区 koreader 包已处理（它装在 /mnt/us 但通过 sh 解释执行入口）。放可执行 ELF 时注意
4. **/etc/uks 是 sqsh loop**：换/加密钥必须重做 uks.sqsh 并保证 loopbacktab 顺序不变（loop 设备号按行序分配，插行会错位）
5. **contentpackd 不能删**：framework 的启动条件 contentpack_font_ready 由它发出；如果哪天想恢复原生系统看某本书，缺了它 framework 永远起不来
6. **powerd 是全系统电源枢纽**：KOReader 的休眠、电量、前光都经 lipc 找 powerd，任何"精简"都不能动 powerd/deviced/lipcd/cmd
7. **otav3/otaupd 删除后**：系统菜单"更新您的 Kindle"入口仍在但会失败——属预期；自制包走 ota-update job 不受影响
8. **首启/重置路径**：删 prereg/register_oobe/langpicker 相关内容后，一旦恢复出厂设置可能卡在 OOBE。建议只禁常驻进程，不删 OOBE 文件
9. **framework_setup.conf 还兼职**：blanket 屏保事件桥接、UPDATE_PWBIN（powerd 固件更新）等。禁 framework 后这些功能消失——KOReader 自己管屏保，可接受，但意味着原生休眠图不再显示
10. **内核/u-boot 签名**（uImage.sig/u-boot.bin.sig）：在 rootfs 之外，自制包若动内核/dtb 仍受底层验签约束；5.16.2.1.1 + LanguageBreak 社区已有成熟结论，刷内核前再核对
11. **ssh(dropear) 默认常驻**：若启用 usbnet 又不设密码/密钥，等于开门。精简时建议顺手禁 sshd.conf 或确认只用密钥登录
